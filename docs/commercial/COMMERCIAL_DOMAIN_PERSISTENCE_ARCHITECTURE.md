## 1. Persistence decision

- PostgreSQL is the relational database of the commercial control plane.
- PostgreSQL **16** is the minimum development compatibility baseline.
- No feature newer than PostgreSQL 16 may be depended on without a later
  explicit architecture change. In particular, native `uuidv7()` is not used.
- PostgreSQL applies only to the commercial control plane.
- The engine's existing durable filesystem lifecycle remains authoritative
  inside the execution plane and is not migrated into PostgreSQL.

Database access technology:

- `pg`;
- hand-written parameterised SQL;
- committed hand-written SQL migrations;
- a small app-owned, checksum-aware migration runner.

Nothing is installed by this document. The migration runner remains subject to
implementation review and must stay deliberately narrow (section 23).

## 3. General relational conventions

- snake_case SQL naming.
- UUID primary keys generated by PostgreSQL `gen_random_uuid()` (UUID v4
  semantics). The application may supply a `crypto.randomUUID()` value where
  it needs an ID before insertion.
- Persisted timestamps are `timestamptz` taken from the database clock.
- Every important constraint and index has an explicit, stable name. Database
  errors are translated to domain errors by constraint name.
- Foreign keys are `ON DELETE RESTRICT`.
- No cascading deletion of commercial authority records.
- No universal `deleted_at`.
- No customer-facing sequential database identifier.

### Text plus CHECK, not native enums

Every status, kind, state, source, actor type and resource type is `text`
constrained by a named `CHECK`. The application mirrors each vocabulary as a
TypeScript/zod union.

Reasons:

- commercial values will evolve;
- CHECK constraints are widened or narrowed through reviewed migrations;
- native enum values cannot be removed, and enum evolution makes forward and
  corrective migrations harder to reason about.

Rollout rule: widen a CHECK in a migration before deploying code that writes a
new value; narrow it only after existing data has been migrated (for example
`ADD CONSTRAINT ... NOT VALID` followed by `VALIDATE CONSTRAINT`).

`audit_events.event_type` is constrained by format only (section 14), because
event types are expected to change most often and are validated against an
application allowlist.

## 4. `users`

```text
users
  id               uuid PK DEFAULT gen_random_uuid()
  idp_issuer       text NOT NULL        -- non-empty, bounded
  idp_subject      text NOT NULL        -- non-empty, bounded
  email            text NULL            -- bounded, NOT unique
  email_verified   boolean NOT NULL DEFAULT false
  status           text NOT NULL DEFAULT 'ACTIVE'   -- ACTIVE | DISABLED
  disabled_at      timestamptz NULL
  created_at       timestamptz NOT NULL DEFAULT now()
  updated_at       timestamptz NOT NULL DEFAULT now()

  CONSTRAINT users_idp_identity_uq UNIQUE (idp_issuer, idp_subject)
  CONSTRAINT users_status_ck       CHECK (status IN ('ACTIVE', 'DISABLED'))
  CONSTRAINT users_disabled_ck     CHECK ((status = 'DISABLED') = (disabled_at IS NOT NULL))
```

Identity authority is `(idp_issuer, idp_subject)`.

- Email is only an attribute. A User is never identified by email.
- Email is not unique: identity providers can assert the same address for
  different principals, and addresses are reassigned.
- No authentication vendor is locked.

## 5. `accounts`

```text
accounts
  id              uuid PK DEFAULT gen_random_uuid()
  kind            text NOT NULL            -- PERSONAL
  owner_user_id   uuid NOT NULL REFERENCES users(id) ON DELETE RESTRICT
  status          text NOT NULL DEFAULT 'ACTIVE'   -- ACTIVE | DISABLED
  disabled_at     timestamptz NULL
  created_at      timestamptz NOT NULL DEFAULT now()
  updated_at      timestamptz NOT NULL DEFAULT now()

  CONSTRAINT accounts_kind_ck     CHECK (kind IN ('PERSONAL'))
  CONSTRAINT accounts_status_ck   CHECK (status IN ('ACTIVE', 'DISABLED'))
  CONSTRAINT accounts_disabled_ck CHECK ((status = 'DISABLED') = (disabled_at IS NOT NULL))

UNIQUE INDEX accounts_personal_owner_uq ON accounts (owner_user_id) WHERE kind = 'PERSONAL'
```

- The only valid kind in schema v1 is `PERSONAL`. `TEAM` is not yet valid data.
- One PERSONAL Account per User, enforced by the partial unique index. The
  index is also the idempotency key for Account provisioning.
- Commercial resources belong to an Account, not directly to a User. This is
  what preserves future team compatibility (section 30).

## 6. `entitlement_grants`

```text
entitlement_grants
  id               uuid PK DEFAULT gen_random_uuid()
  account_id       uuid NOT NULL REFERENCES accounts(id) ON DELETE RESTRICT
  kind             text NOT NULL     -- FREE_BYO | HOSTED_TRIAL | CREATOR
  state            text NOT NULL     -- AVAILABLE | RESERVED | CONSUMED | REVOKED | EXPIRED
  source           text NOT NULL     -- ACCOUNT_PROVISIONING
  issuance_key     text NOT NULL     -- bounded, constrained format
  policy_version   text NOT NULL     -- non-empty, bounded
  issued_at        timestamptz NOT NULL DEFAULT now()
  reserved_at      timestamptz NULL
  consumed_at      timestamptz NULL
  revoked_at       timestamptz NULL
  expired_at       timestamptz NULL
  expires_at       timestamptz NULL  -- scheduled expiry; semantics decided later
  updated_at       timestamptz NOT NULL DEFAULT now()

  CONSTRAINT entitlement_grants_kind_ck   CHECK (kind IN ('FREE_BYO', 'HOSTED_TRIAL', 'CREATOR'))
  CONSTRAINT entitlement_grants_state_ck  CHECK (state IN ('AVAILABLE', 'RESERVED', 'CONSUMED', 'REVOKED', 'EXPIRED'))
  CONSTRAINT entitlement_grants_source_ck CHECK (source IN ('ACCOUNT_PROVISIONING'))
  CONSTRAINT entitlement_grants_v1_issuable_kind_ck CHECK (kind = 'FREE_BYO')
  CONSTRAINT entitlement_grants_account_scope_uq UNIQUE (account_id, id)   -- composite-FK target
```

- `HOSTED_TRIAL` and `CREATOR` exist as domain vocabulary only.
  `entitlement_grants_v1_issuable_kind_ck` prevents inserting them. A later
  reviewed migration removes that constraint when issuance of another kind is
  approved.
- `source` is `ACCOUNT_PROVISIONING` only in schema v1.
- `policy_version` identifies the versioned commercial policy under which the
  grant was issued. It carries no numeric allowance. Its naming convention is
  unresolved (section 32).
- No commercial limit is stored on the grant.

## 7. Initial FREE_BYO invariant

Two database-level guarantees, both independent of grant state.

### 7.1 Generic issuance idempotency

```text
CONSTRAINT entitlement_grants_issuance_uq
  UNIQUE (account_id, kind, source, issuance_key)
```

Replaying the same issuance operation cannot create a second grant.

### 7.2 Initial free-grant uniqueness

```sql
CREATE UNIQUE INDEX entitlement_grants_initial_free_byo_uq
ON entitlement_grants (account_id)
WHERE kind = 'FREE_BYO'
  AND source = 'ACCOUNT_PROVISIONING';
```

This applies regardless of grant state. Therefore:

- `AVAILABLE -> CONSUMED` does not enable another initial free grant;
- revocation does not enable another initial free grant;
- expiration does not enable another initial free grant;
- an accidentally different `issuance_key` cannot create another
  account-provisioned `FREE_BYO`.

A uniqueness rule restricted to `state = 'AVAILABLE'` is prohibited, because
it would allow re-issuance after consumption or revocation.

Future promotional or administrative grants may use other sources, introduced
by later migrations.

## 8. Grant timestamp integrity

```text
CONSTRAINT entitlement_grants_reserved_at_ck CHECK (state <> 'RESERVED' OR reserved_at IS NOT NULL)
CONSTRAINT entitlement_grants_consumed_at_ck CHECK (state <> 'CONSUMED' OR consumed_at IS NOT NULL)
CONSTRAINT entitlement_grants_revoked_at_ck  CHECK (state <> 'REVOKED'  OR revoked_at  IS NOT NULL)
CONSTRAINT entitlement_grants_expired_at_ck  CHECK (state <> 'EXPIRED'  OR expired_at  IS NOT NULL)
```

- Historical timestamps may remain populated after later transitions.
- The application/domain layer owns allowed transition sequencing.
- The full state machine is not encoded in one SQL CHECK.

## 9. `productions`

```text
productions
  id                             uuid PK DEFAULT gen_random_uuid()
  account_id                     uuid NOT NULL REFERENCES accounts(id) ON DELETE RESTRICT
  title                          text NOT NULL
  creation_entitlement_grant_id  uuid NOT NULL
  created_by_user_id             uuid NOT NULL REFERENCES users(id) ON DELETE RESTRICT
  creation_idempotency_key       text NULL      -- bounded
  archived_at                    timestamptz NULL
  created_at                     timestamptz NOT NULL DEFAULT now()
  updated_at                     timestamptz NOT NULL DEFAULT now()

  CONSTRAINT productions_account_scope_uq UNIQUE (account_id, id)   -- composite-FK target for future children
  CONSTRAINT productions_creation_grant_same_account_fk
    FOREIGN KEY (account_id, creation_entitlement_grant_id)
    REFERENCES entitlement_grants (account_id, id) ON DELETE RESTRICT

UNIQUE INDEX productions_creation_idempotency_key_uq
  ON productions (account_id, creation_idempotency_key)
  WHERE creation_idempotency_key IS NOT NULL
INDEX productions_account_list_ix ON productions (account_id, created_at DESC, id)
INDEX productions_creation_grant_ix ON productions (creation_entitlement_grant_id)
```

- `creation_entitlement_grant_id` is **NOT NULL**. Every commercial Production
  retains permanent provenance identifying the EntitlementGrant that authorised
  its creation.
- The composite same-Account foreign key makes it structurally impossible for
  a Production to reference another Account's grant.
- The provenance reference is not usage accounting. Usage (runtime, shots,
  generations) belongs to a future UsageLedger.
- No Production status column exists in schema v1. Archival is `archived_at`.
- A Production stores none of: `EP##` identifiers, scene or shot IDs, an engine
  namespace, a filesystem path, a media-root path, or a provider execution
  identity.

## 10. Production cardinality

- The schema permits many Productions per Account.
- There is no unique Account-to-Production constraint.
- The initial first-production restriction is entitlement policy, not
  relational cardinality.
- Archived Productions continue to count toward the initial entitlement policy
  unless a later commercial policy explicitly changes that rule. Archiving
  does not reset free eligibility.

## 11. Production title

- The application normalises the title before insertion.
- The database rejects empty and whitespace-only titles, requires the stored
  value to be already trimmed, and bounds its length:

```text
CONSTRAINT productions_title_ck
  CHECK (title = btrim(title) AND char_length(title) BETWEEN 1 AND <bound>)
```

- The exact bound is fixed during migration `0001` review (the R44B2A proposal
  is 200 characters).
- Display normalisation beyond trimming belongs to application code.

---

## 12. Production creation idempotency

- `creation_idempotency_key` is optional and unique per Account when present.
- A repeated request with the same key returns the existing Production when it
  represents the same canonical creation request.
- For the initial title-only contract, the canonical (normalised) title is
  compared. Reusing a key with a different title is an explicit domain
  conflict, never a silent success.
- No generic idempotency table is introduced.

## 13. First-production transaction

Isolation: `READ COMMITTED`.

1. Derive the User and Account from authenticated server context.
2. Require an active User and an active Account.
3. Ignore any client-supplied Account authority.
4. When an idempotency key is supplied, resolve an existing Production by
   `(account_id, creation_idempotency_key)` and apply section 12.
5. Lock the applicable `FREE_BYO` grant with `SELECT ... FOR UPDATE`.
6. Evaluate the versioned first-production policy.
7. Count Productions already created under that grant, including archived
   Productions.
8. Refuse when the policy does not permit another Production.
9. Insert the Production.
10. Insert the `production.created` AuditEvent.
11. Commit atomically.

The grant-row lock serialises concurrent creation attempts. After waiting for
the lock, PostgreSQL re-evaluates the row against the query's conditions, so a
grant whose state changed is excluded.

If a later policy counts across several grants, the Account row is locked with
`FOR NO KEY UPDATE` instead (plain `FOR UPDATE` on the Account would block
concurrent foreign-key inserts that reference it).

The current one-production policy is not encoded as a permanent uniqueness
constraint.

### Production creation does not consume the grant (locked)

- A new Production requires a qualifying `FREE_BYO` grant in `AVAILABLE`.
- Creating the Production does not mutate the grant. Its state stays
  `AVAILABLE`, and `reserved_at`, `consumed_at`, `revoked_at`, `expired_at`,
  `expires_at` and `updated_at` are not modified because a Production was
  created. Production creation is never a reservation, consumption,
  revocation or expiry.
- `free-byo-v1` permits one Production per qualifying grant. The limit is
  enforced by counting Productions bound to the grant through
  `creation_entitlement_grant_id`.
- Archived Productions remain included in that count, so archiving does not
  restore `FREE_BYO` capacity.
- Actual reservation and consumption semantics belong to the later
  generation/value-delivery authority and must be defined there.
- The `FOR UPDATE` grant-row serialisation above, the Production provenance
  rules (section 9) and the idempotency rule (section 12, including the
  different-title conflict) are unchanged.

## 14. `audit_events`

```text
audit_events
  id              uuid PK DEFAULT gen_random_uuid()
  sequence        bigint GENERATED ALWAYS AS IDENTITY UNIQUE
  occurred_at     timestamptz NOT NULL DEFAULT now()
  account_id      uuid NULL REFERENCES accounts(id) ON DELETE RESTRICT
  actor_type      text NOT NULL       -- USER | SYSTEM
  actor_user_id   uuid NULL REFERENCES users(id) ON DELETE RESTRICT
  event_type      text NOT NULL       -- resource.past_tense_action
  resource_type   text NOT NULL       -- user | account | entitlement_grant | production
  resource_id     uuid NOT NULL
  correlation_id  uuid NOT NULL
  metadata        jsonb NOT NULL DEFAULT '{}'

  CONSTRAINT audit_events_actor_type_ck    CHECK (actor_type IN ('USER', 'SYSTEM'))
  CONSTRAINT audit_events_actor_ck         CHECK ((actor_type = 'USER') = (actor_user_id IS NOT NULL))
  CONSTRAINT audit_events_event_type_ck    CHECK (event_type ~ '^[a-z][a-z_]*\.[a-z][a-z_]*$')
  CONSTRAINT audit_events_resource_type_ck CHECK (resource_type IN ('user', 'account', 'entitlement_grant', 'production'))
  CONSTRAINT audit_events_metadata_ck      CHECK (jsonb_typeof(metadata) = 'object' AND octet_length(metadata::text) <= <bound>)

INDEX audit_events_account_ix     ON audit_events (account_id, sequence)
INDEX audit_events_resource_ix    ON audit_events (resource_type, resource_id)
INDEX audit_events_correlation_ix ON audit_events (correlation_id)
```

Event naming: `resource.past_tense_action`, for example:

- `user.provisioned`
- `account.provisioned`
- `entitlement_grant.issued`
- `production.created`
- `account.disabled`

- AuditEvents are written by the application in the same transaction as the
  mutation they record. Triggers do not write audit events, because they have
  no actor or correlation context.
- Metadata is small, structured, non-sensitive and validated per event type by
  the application. State transitions are recorded as
  `{"from": "...", "to": "..."}`.
- Full row snapshots are not stored.
- The metadata size bound is fixed during migration `0001` review (the R44B2A
  proposal is 4096 bytes).

---

## 15. Audit ordering

- `sequence` provides stable numeric ordering for navigation.
- `sequence` is **not** proof of commit chronology. Concurrent transactions
  obtain sequence values independently of the order in which they commit.
- `correlation_id` links the events of one transaction or workflow.
- `occurred_at` is the event timestamp (database transaction time).
- No cryptographic or causal ordering guarantee is implied.

---

## 16. Audit immutability

Primary protection is privilege:

- the runtime database role has `INSERT` and `SELECT` on `audit_events`;
- it has no `UPDATE` and no `DELETE`.

Defence in depth: a `BEFORE UPDATE OR DELETE` trigger rejects the operation.

The trigger does **not** make the table immutable to the database owner, the
migration owner or a PostgreSQL superuser; those authorities can alter or
bypass database objects.

The v1 audit log is operationally append-only, not cryptographically
tamper-evident. A stronger transparency or integrity mechanism requires a
separate future architecture decision.

---

## 17. Audit metadata prohibition

Audit metadata must never contain:

- provider secrets;
- API keys;
- authentication tokens;
- access or refresh tokens;
- cookies;
- session credentials;
- a raw Authorization header;
- a raw request body;
- database credentials;
- filesystem paths;
- media-root paths;
- customer email.

Actors and resources are identified by internal UUIDs.

Recording IP address or user agent is an unresolved privacy decision.

## 18. Provisioning transaction

Isolation: `READ COMMITTED`.

1. Insert or select the User by `(idp_issuer, idp_subject)`
   (`INSERT ... ON CONFLICT DO NOTHING RETURNING`, then `SELECT` when no row
   was returned).
2. Update allowed identity attributes (`email`, `email_verified`) from
   verified server-side identity claims.
3. Never automatically reactivate a disabled User; refuse provisioning for a
   disabled User.
4. Insert or select the PERSONAL Account through
   `accounts_personal_owner_uq`.
5. Insert the initial `FREE_BYO` grant
   (`kind = 'FREE_BYO'`, `state = 'AVAILABLE'`,
   `source = 'ACCOUNT_PROVISIONING'`) with `ON CONFLICT DO NOTHING`.
6. Rely on database uniqueness for concurrency and idempotency.
7. Write AuditEvents only for objects actually created by this transaction.
8. Use one shared correlation ID.
9. Commit atomically.

No grant kind, source or policy authority comes from the browser.

Concurrent first logins must yield exactly:

- one User;
- one PERSONAL Account;
- one initial `FREE_BYO` grant;
- one set of creation AuditEvents.

## 19. Transaction strategy

| Operation | Mechanism |
|---|---|
| Provisioning | `READ COMMITTED` + unique constraints + `ON CONFLICT` |
| Production creation | `READ COMMITTED` + `FOR UPDATE` on the applicable grant |
| Audit | Same transaction as the mutation |
| Future Hosted Trial | Grant-row lock + GenerationAuthorization uniqueness when that table is introduced |
| Migrations | Transaction + migration-runner advisory lock |

- `SERIALIZABLE` is not used by default.
- Advisory locks are not used for normal domain operations.

## 21. Privacy and erasure boundary

Locked:

- unnecessary personal attributes must be erasable or pseudonymisable;
- audit metadata intentionally avoids customer PII;
- audit records identify actors primarily by internal UUIDs;
- disabled User/Account semantics are separate from privacy erasure;
- anti-reprovisioning and free-entitlement abuse requirements must be
  reconciled with privacy obligations before public signup.

Not decided: whether `idp_issuer`/`idp_subject` is deleted, replaced, hashed,
tombstoned, or retained under a fraud-prevention policy.

Reason: removing the authoritative external identity may allow the same person
to provision another User, Account and `FREE_BYO` grant, while retaining a
derived identifier can remain personal data requiring a justified legal basis
and retention policy.

This is a public-launch blocker, not a schema-v1 implementation blocker.

## 22. Database access technology

`pg`, with:

- one application-owned Pool;
- parameterised SQL only;
- hand-written repository/query functions;
- zod validation of returned rows;
- explicit database error translation by named constraint.

No ORM in v1.

Rejected for this architecture:

- **Prisma.** Its schema language does not express the required CHECK,
  partial-index and composite foreign-key invariants well, which would push
  the critical rules into raw SQL anyway, and it adds a generated client and
  query engine.
- **Drizzle.** Its TypeScript schema would have to mirror every CHECK, and its
  generated migrations would make generated SQL the review surface.
- **Kysely as the initial persistence layer.** It adds a dependency and row
  typing work that five tables do not justify. Kysely remains a possible future
  query layer over the same PostgreSQL schema and `pg` Pool if complexity later
  justifies it.

## 23. Migration discipline

Location: `apps/commercial-api/migrations/`

Naming: `NNNN_descriptive_name.sql`

- Committed to Git.
- Deterministic numeric order.
- Hand-reviewed SQL.
- Forward-only; corrections are later compensating migrations.
- No automatic migration on API startup.
- An explicit migration command.
- Each migration runs in a transaction where PostgreSQL permits.
- The runner holds an advisory lock while migrating.
- The SHA-256 of every applied migration is recorded.
- A modified checksum for an already-applied migration is a hard failure.
- A separate test database.

The runner owns and bootstraps only the `schema_migrations` infrastructure
required to track migrations:

```text
schema_migrations
  version     integer PK
  name        text NOT NULL
  sha256      char(64) NOT NULL
  applied_at  timestamptz NOT NULL DEFAULT now()
```

Production never executes uncommitted or generated schema mutations.

## 24. Database roles

### Migration role

- Owns schema/DDL authority.
- Used only by the explicit migration command.

### Runtime API role

- No DDL.
- No `DELETE` in schema v1.
- Domain permissions limited to what repository operations require.
- On `audit_events`: `SELECT` and `INSERT` only; no `UPDATE`, no `DELETE`.

A PostgreSQL superuser is never used for application runtime.

## 27. Pool lifecycle and readiness

Future process lifecycle:

1. load and validate database configuration;
2. construct one Pool;
3. verify connectivity;
4. verify the expected migration/schema state;
5. start accepting application traffic;
6. on shutdown, close the HTTP server first;
7. then close the Pool.

`GET /__health` keeps its current liveness-only contract and does not depend
on PostgreSQL.

Future `GET /__ready` may return:

- `200` when dependencies and schema are ready;
- `503` with stable, non-sensitive JSON when they are not.

Readiness is implemented later.

## 28. Real PostgreSQL testing

Database correctness is tested against actual PostgreSQL. Mocks and in-memory
substitutes cannot establish:

- concurrent unique-conflict behaviour;
- `FOR UPDATE` serialisation;
- `ON CONFLICT` behaviour;
- composite foreign-key behaviour;
- CHECK enforcement;
- partial indexes;
- privilege behaviour;
- trigger behaviour;
- migration locking.

The future `test:db` command fails when its dedicated test-database
configuration is absent. It never silently skips persistence integration
tests.

Docker and Testcontainers are not introduced by this lock.

## 29. Required concurrency tests

### Concurrent provisioning

Approximately 20 parallel attempts for the same external identity result in
exactly:

- 1 User;
- 1 PERSONAL Account;
- 1 initial account-provisioned `FREE_BYO` grant;
- 1 set of corresponding provisioning AuditEvents.

### Concurrent first Production

Parallel creation attempts under the initial first-production policy produce
only the number of Productions the policy allows.

### Future Hosted Trial

Parallel reservation attempts must prove single consumption against real
PostgreSQL.
